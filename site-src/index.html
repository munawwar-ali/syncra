The problem

Syncra is a sync engine: software that keeps the same data identical across many users' devices, even when some of them are offline.

Everyone wants Google Docs-style apps. Almost nobody wants to build the sync.

Apps like Google Docs, Notion and Figma let several people edit the same thing at once. They keep working when the internet drops, and they merge everyone's changes afterwards without losing work. This is hard to build.

What users now expect

Open the same file together, keep typing in a tunnel, and find nothing lost afterwards.

What most developers do instead

Most don't want to build it themselves, so they rent a hosted service, or they accept losing data.

1

Work gets lost

Forms fail to save, edits vanish on reconnect, and users learn not to trust the app. Offline support is usually bolted on late and never finished.

2

Conflicts overwrite people

When two people change the same thing, a simple "last write wins" rule silently throws one of them away. Hand-written merge logic is where the subtle bugs live.

3

Sync is locked up or half-built

Hosted platforms are convenient but closed, and your data and pricing live on their terms. Rolling your own on Yjs gives you merging, but you still build the server, auth, quotas, history and admin tools yourself.

What already exists

Good tools exist. None filled this exact gap.

There is no shortage of sync and collaboration products. They tend to fall into four groups: hosted and closed, bare Yjs servers, relational sync, and other CRDT ecosystems. Syncra sits where Yjs documents, self-hosting and a ready platform meet.

Why Syncra

Yjs does the merging. Syncra does everything else.

Syncra does not invent a new CRDT. All merging is done by Yjs. Syncra adds what an app still needs around it, so you can ship offline-first features without building a sync backend first.

Persistent, multi-tenant server

Per-tenant token signing, API keys, roles, quotas and rate limits.

A client runtime that survives reality

IndexedDB storage, an offline outbox, reconnect with backoff and jitter, and multi-tab leader election.

You own it

One Docker Compose file runs the server, worker, databases, dashboard and monitoring. Your data stays in your PostgreSQL.

How it works

Edit anywhere. Converge everywhere.

1. Edit with no network

Changes are applied to the local document instantly and stored in IndexedDB. Nothing waits on a server.

2. Reconnect

The client reconnects with backoff and jitter, and sends only what changed since the server last saw it.

3. Merge, no dialogs

Text and lists merge automatically through Yjs. The server commits to PostgreSQL, acknowledges, and broadcasts to other subscribers.

Offline-first client

IndexedDB storage, outbox, reconnect with backoff and jitter, multi-tab leader election.

Delta sync

Over WebSockets, with HTTP pull/push endpoints for networks that block them.

Reliable delivery

At-least-once delivery with idempotent operations. A write is acknowledged only after it is committed.

Multi-tenant security

Per-tenant token signing, API keys, roles, quotas, rate limits, and an audit log with a hash chain.

History and restore

Time-travel view and non-destructive restore, plus snapshots and verified compaction.

Presence

Live cursors across nodes.

Change feed and webhooks

Server-sent events and signed webhooks, so you can feed your own search or index.

Dashboard

Live monitor, document inspector, keys, usage, webhooks, members, audit and a playground.

Observability

Prometheus metrics, a Grafana dashboard and alert rules.

Horizontal scale

Sync nodes behind nginx, PostgreSQL shards, and Redis for cross-node hints. Losing Redis delays fan-out but loses no data.

REST API

Documented with OpenAPI. List, read and export documents as JSON.

React bindings

useDoc, useYMap and useSyncStatus hooks over the client SDK.

Developer experience

A few lines to a synced component.

Create a client, wrap your app, and read a shared document like any other state. The packages are not published to npm yet, so use the workspace packages in the repository.

Read the SDK guide 
import { createClient } from '@syncra/client';
import { SyncraProvider, useDoc, useYMap, useSyncStatus } from '@syncra/react';

const client = createClient({
  url: 'http://localhost:8080',
  publishableKey: 'pk_live_...',
  getToken: () => fetch('/api/syncra-token')
    .then((r) => r.json()).then((j) => j.token),
});

function Todo({ id }) {
  const { doc } = useDoc('todos', id);
  const todo = useYMap(doc);
  const { connection, pendingOps } = useSyncStatus();
  return (
    <label>
      <input type="checkbox" checked={todo.done ?? false}
        onChange={(e) => doc?.setFields({ done: e.target.checked })} />
      {todo.title} ({connection}, {pendingOps} unsynced)
    </label>
  );
}
Architecture

Simple path, durable by design.

Clients keep a local copy of each document and send Yjs updates to a sync node. The node appends them to a PostgreSQL shard, acknowledges the commit, and broadcasts to other subscribers. A worker writes snapshots, verifies them, and compacts old operations.

Measured, not claimed

Numbers, with the caveats.

Every figure comes from committed scripts and result files, measured on one laptop with the server and load generator sharing CPU.

1,000connected clients, 0 errors and 0 drops
~26xless data on reconnect: 3,884 bytes instead of 102,016 after 100 edits to a 102 KB document
2.8-3.5xfaster cold load after compacting a 20,000-operation document

Honest limits

  • The latency target (ack p95 under 100 ms) was not met: p95 ranged 147-657 ms across 3 runs.
  • Multi-node behaviour, 5,000 connections and node-failure recovery have not been measured.
  • Young project: no production users and no third-party security audit.
  • No queries, no end-to-end encryption, no relational data. Documents are capped at 1 MiB.
